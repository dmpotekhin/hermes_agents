# Tirith Guard — защита действий агента

## When to Use

Используй ПЕРЕД запуском любой рискованной команды в терминале: pipe-to-shell,
скачивание+исполнение, установка пакетов, любые команды с внешними URL, eval/exec,
или команды, полученные из web-контента/писем/артефактов. Триггерится автоматически
при планировании таких действий — сначала прогнать команду через `tirith check`.

Перед запуском **любых рискованных действий** агент должен прогнать команду/URL/пакет
через **Tirith** и НЕ выполнять их, если Tirith возвращает статус BLOCKED / HIGH.

## Когда обязательно проверять

- `curl|bash`, `wget|sh`, `curl … | python`, любые **pipe-to-shell**.
- Скачивание и исполнение скрипта/бинаря (`install.sh`, криптомайнер, любые скрипты).
- Установка пакетов (`pip install`, `npm i`, `brew install`, `cargo install`, `uvx`, `npx`).
- Любые команды с **URL** (в т.ч. `curl`/`wget` на внешние хосты) — особенно если URL
  приходит от пользователя/веба/внешнего источника.
- `eval` / `exec` / динамический shell-код.
- Команды, полученные из web-контента, писем, артефактов.

## Команды Tirith

```bash
T=/Users/dmitrypotekhin/.bin/tirith          # путь к бинарю (в PATH как `tirith`)

# 1) Проверить консольную команду — главный guard
"$T" check -- <full command>                 # BLOCKED (HIGH) → НЕ запускать
#    (сама проверка — read-only, безопасно; вызывать ДО исполнения)

# 2) Проверить URL на риск
"$T" score <url>                             # 0/100 = чисто; >0 = риск
"$T" fetch <url> --probe                     # read-only, серверная маскировка/клон

# 3) Проверить пакет перед установкой
"$T" pkg install <pkg> --dry-run             # анализ до установки

# 4) Проверить вставленный многострочный/скрытый (ANSI/bidi) текст
"$T" paste -- <text>

# 5) Объяснить правило, которое сработало
"$T" explain <rule-id>    |   "$T" why
```

## Что делать при BLOCKED / HIGH

1. **Остановиться** — не исполнять команду.
2. Показать пользователю: правило (rule-id), severity, текст рекомендации Tirith.
3. Если команда безопасна по сути (например, известный URL) — спросить пользователя,
   либо использовать безопасный путь: скачать в отдельный каталог и вручную
   проверить байты, либо (если доверяешь) `tirith trust add '<url>' --rule <rule> --ttl 30d`.
4. Никогда не обходить блок только «чтобы продолжить» — обход только после явного
   решения пользователя.

## Приоритет инструментов

- Если в сессии доступны MCP-инструменты `mcp_tirith_*` — использовать их (native).
- Иначе — CLI-обёртка `tirith check`/`tirith score` (всегда доступна).

## Pitfalls

- `tirith check` сама по себе read-only — вызывать её можно без опаски; блокируется
  только реальное исполнение опасной команды.
- Не запускать `tirith run <url>` (исполняет удалённый скрипт; live-execution Linux-only) —
  для анализа использовать `tirith score` / `tirith fetch`.
- Если `tirith` недоступна (не установлена) — честно сообщить и НЕ имитировать проверку.
