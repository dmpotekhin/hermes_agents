# Updating a generated / self-installing third-party plugin safely

Class of task: a Hermes plugin whose files are GENERATED by an upstream repo's build script
(`convert.sh` / `build-*.py` / `install.sh`), installed into `<HERMES_HOME>/plugins/...`, and
possibly wired into `config.yaml` by that script. Verified end-to-end on
`msitarzewski/agency-agents` → `agency-agents-router` (2026-09-18, Hermes v0.21.0).

Naive `git pull && ./install.sh` is the wrong move: these installers `rm -rf` the destination and
rewrite config — including, in older versions, corrupting `plugins.enabled`.

## 0. Classify
Plugin refresh = **quick-win** (plugin dir + maybe one config line). Announce it, don't run the
full feature ceremony.

## 1. What is upstream actually ahead by?
```bash
curl -s "https://api.github.com/repos/<owner>/<repo>/commits?per_page=10" -o /tmp/c.json
python3 -c "import json;d=json.load(open('/tmp/c.json'));[print(c['sha'][:8],c['commit']['author']['date'][:10],c['commit']['message'].splitlines()[0]) for c in d]"
```
Read the messages for changes that touch YOUR integration (`fix(hermes): …`, `fix(install): …`).
Note: `web_extract` on github.com / api.github.com may be blocked in this environment while plain
`curl` from the terminal works — use the terminal, and write the JSON to a file rather than piping
into a `python3 -c` heredoc if the safety hook is touchy.

## 2. Prove the installed copy is pristine (provenance)
Before overwriting anything, answer "do I lose local edits?". If the generated output is
**gitignored upstream**, git history can't help — rebuild it instead:

```bash
git clone --depth 1 <url> /tmp/src && cd /tmp/src
git fetch --depth 1 origin <install_time_full_sha> && git checkout FETCH_HEAD   # need the FULL sha
./scripts/convert.sh --tool hermes --out /tmp/gen_installtime
shasum -a 256 /tmp/gen_installtime/hermes/<plugin>/{__init__.py,plugin.yaml} \
              "$HERMES_HOME/plugins/<plugin>"/{__init__.py,plugin.yaml}
```
Identical hashes ⇒ no local edits, the overwrite is safe. Then generate the CURRENT build into a
separate dir (e.g. `/tmp/agency-new/`) to copy from later. Get the full sha from the commits API —
`git fetch <short-sha>` fails with `could not find remote ref`.

## 3. Probe the new plugin against the INSTALLED runtime (before installing)
A plugin update can require a newer host API. Grep the installed Hermes source for the symbols the
new plugin uses:
```bash
search_files pattern='subagent_lifecycle|class SubagentLaunchRequest' path=<hermes-agent dir>
```
and then verify the SIGNATURES with the Hermes venv interpreter (fake-context probe): see
`scripts/probe_hermes_plugin.py`. Confirmed compatible when the fields/methods the plugin passes as
KEYWORDS exist (`launch`, `wait(handle, timeout_seconds=…)`, `cancel(handle, reason=…)`, `result`).

## 4. Install — backup, then surgical copy
```bash
BK="$HERMES_HOME/.backup-<plugin>-$(date +%Y%m%d-%H%M%S)"
cp -R "$HERMES_HOME/plugins/<plugin>" "$BK"          # rollback = cp -R back
cp /tmp/new/<plugin>/{plugin.yaml,__init__.py,data/agents.json} "$HERMES_HOME/plugins/<plugin>/"
printf 'source: <url>\ncommit: %s\ninstalled: %s\n' <sha> "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  > "$HERMES_HOME/plugins/<plugin>/.upstream-commit"
```
Put backups OUTSIDE the plugins tree (a sibling hidden dir under the profile) so Hermes never
scans them as a plugin. Don't `rm -rf` the destination — copy over only the files that changed.

## 5. Verify (in this order)
1. **Upstream's own tests, against the INSTALLED files.** Their suites usually derive the plugin
   path from `<root>/integrations/<tool>/<plugin>`, so point a throwaway root at the install:
   ```bash
   mkdir -p /tmp/plugintest/scripts /tmp/plugintest/integrations/hermes
   cp /tmp/src/scripts/test-<tool>-plugin.py /tmp/plugintest/scripts/
   ln -s "$HERMES_HOME/plugins/<plugin>" /tmp/plugintest/integrations/hermes/<plugin>
   python3 /tmp/plugintest/scripts/test-<tool>-plugin.py     # expect: Ran N tests … OK
   ```
2. **Load + register + call handlers** on the real runtime → `scripts/probe_hermes_plugin.py`.
3. **Host registry state**: `hermes plugins list` → `enabled` (parse by `│`, not grep).
4. **Toolsets actually loaded**: `hermes tools list` → `✓ enabled <toolset>  🔌 <Name>`.
5. **Config untouched by the update** (`grep -A3 '^plugins:' config.yaml`).

## 6. Report, and be honest about leftovers
State: old → new version/count delta, what was verified and HOW, backup paths, and anything still
broken. Restart note: plugin tools register at STARTUP, so the running session and the gateway keep
the old state — `hermes gateway restart` (Telegram) / new session (CLI).

## Gotchas that actually bit
- Plugin discovery is **profile-scoped**: `<profile>/plugins/` only, when `HERMES_HOME` is a named
  profile. A plugin in the base `~/.hermes/plugins/` is invisible there — prove it with
  `HERMES_HOME=$HOME/.hermes hermes plugins list`.
- `hermes plugins list`'s table WRAPS descriptions; grepping for a plugin name can match another
  plugin's description cell and produce a false status. Parse the row cells.
- Probe-script arity: a plugin's entry point is `register(ctx)` (ONE arg) and the tool handlers are
  `handler(args)` (ONE arg) — the plugin context is captured by closure, so `handler(args, ctx)`
  raises `TypeError: takes 1 positional argument but 2 were given`. Inspect signatures, don't guess.
- Approval-gated terminal commands can time out (default `approvals.timeout: 60`) while the user is
  away; that is a transient gate, not a broken tool. Don't retry-loop — restructure, and keep the
  read-only checks going so the report is still useful.
- `hermes config set` on a LIST key stringifies it; the same class of bug as the glued scalar,
  both invisible until you `yaml.safe_load` and check the type.
