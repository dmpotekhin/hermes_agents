# Launchd-служба для долгоживущего процесса (проверено на macOS 12.7.6)

Задача: бот/сервер должен подниматься при входе в систему и перезапускаться после падения,
а не жить в фоновой сессии агента.

## Порядок

1. Сначала остановить все ручные копии процесса: два инстанса с long-polling Telegram
   конфликтуют (`getUpdates` терминируется другим запросом).
2. Юнит: `~/Library/LaunchAgents/<label>.plist`. Обязательные ключи:
   - `ProgramArguments` — абсолютный путь к интерпретатору venv и скрипту;
   - `WorkingDirectory` — каталог проекта (приложение само читает `.env` из cwd через
     `load_dotenv()`); launchd НЕ наследует окружение шелла;
   - `EnvironmentVariables` → `PATH` = `/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin`
     (иначе Homebrew-утилиты вроде `ffmpeg`, `yt-dlp` не находятся);
   - `RunAtLoad` = true, `KeepAlive` = true;
   - `StandardOutPath` и `StandardErrorPath` — ОДИН и тот же файл: логи Python идут
     в stderr, при двух разных путях половина лога уезжает в `.err.log`.
3. Проверить синтаксис: `plutil -lint <plist>` → `OK`.
4. Загрузить: `launchctl bootstrap gui/$(id -u) <plist>`
   (на старых системах — `launchctl load -w <plist>`); остановить:
   `launchctl bootout gui/$(id -u)/<label>`.
5. Статус: `launchctl list | grep <label>` → `PID\tкод_выхода\tlabel`.
   Код `-15` = процесс убит SIGTERM (норма после ручной остановки).

## Проверка, что служба поднялась после перезапуска

`launchctl kickstart -k gui/$(id -u)/<label>` (или `bootout` → `bootstrap`) убивает текущий
процесс и запускает новый. После этого:

- `launchctl list | grep <label>` → непустой PID = процесс живой, отличай его от кода выхода
  предыдущего инстанса (`-9` = убит SIGKILL от `kickstart -k`, `-15` = SIGTERM от остановки).
- `ps -p <PID> -o pid,etime,command` — сколько процесс уже живёт; для скрипта на Python
  абзац `etime` в первые секунды означает, что он только импортирует зависимости, а не упал.
- **Лог может молчать при живом процессе:** stdout по `StandardOutPath` — блочно буферизованный,
  стартовые строки появляются пачками (или только при следующем сбросе буфера). Отсутствие
  свежих строк в первые десятки секунд НЕ означает падение. Проверяй по артефакту, который
  процесс обязан создать (файл БД, PID-файл, сокет), а не по логу; при сомнении — `lsof -p <PID>`.
- Если после перезапуска в логе нет и стартовых строк, и артефакта — смотри полный лог целиком:
  строки о старте могли прийти с задержкой ПОСЛЕ диагностики.

## Проверка, что KeepAlive работает

`kill <PID>` из `launchctl list`, подождать ~15 секунд и убедиться, что появился НОВЫЙ PID
и в логе снова `Start polling`. Без этой проверки юнит считается неготовым.

## Мелочи, которые экономят время

- Привычный путь к логу сохраняется симлинком:
  `ln -sfn ~/Library/Logs/<name>.log /tmp/<name>.log` (сначала перенести старый файл,
  `ln -sfn` перезапишет обычный файл симлинком).
- Пароль/токен службе НЕ передавать через plist: `.env` читает само приложение.
- Правки plist не применяются на лету: `bootout` → `bootstrap`.
- После смены кода службу надо перезапустить: `KeepAlive` держит старую версию в памяти.
