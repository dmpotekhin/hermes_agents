# News aggregation and digest pipeline

Класс задач: превратить бота или приложение в персональный «радар» — собирать материалы из
внешних источников (RSS/Atom, релизы GitHub, YouTube-фиды, веб-страницы), отсеивать шум,
размечать материалы, считать личную релевантность и присылать дайджесты по расписанию в чат и
в хранилище заметок. Применимо к любому хосту (Telegram-бот, сервис, CLI): правила ниже не
зависят от конкретного репозитория.

Готовый каркас модулей, контракты и группы настроек: `references/pipeline-anatomy.md`.

## Незыблемые правила

- **Дополнять, а не переписывать.** Новая подсистема = отдельный пакет + один роутер/хендлер;
  существующие пути хоста трогаются только в точках интеграции (задача планировщика, кнопка,
  регистрация роутера, префикс callback-данных). Перед правкой хоста — аудит: где уже есть
  LLM-роутер, кэш, квоты, планировщик, хранилище, канал доставки, контроль доступа. Всё это
  переиспользуется, а не дублируется.
- **LLM — ассистент, а не источник правды.** Он суммирует, классифицирует, связывает; он не
  додумывает факты. Оригинальный URL обязателен у каждого материала и печатается в карточке.
- **Signal, not volume.** Цель — 10-15 минут чтения в день: жёсткая фильтрация, мало материалов,
  никакого «отдадим всё, что собрали».
- **Каждая документируемая переменная окружения должна кем-то читаться.** Настройка без
  потребителя удаляется, а не описывается «на будущее». Пустой конфиг обязан давать рабочие
  значения по умолчанию.

## Процедура

1. **Аудит хоста до кода.** Найти и записать: абстракцию LLM (роутер/клиент), кэш и квоты,
   паттерн планировщика (in-process цикл? cron? отдельный воркер), хранилище, канал доставки,
   контроль доступа, способ подключения роутеров, конвенции вывода (parse_mode, длина сообщения).
   План с инвентарём источников пишется до первой строки кода.
2. **Проверить каждый источник живым запросом.** Скрипт по списку кандидатов: печатать статус,
   тип и число элементов; рабочие — в реестр, у битых искать альтернативный адрес (проверяя его
   тем же способом), у источников без стабильного фида — пометить выключенными, а не выдумывать
   URL. Реестр — данные, а не код: группа, приоритет, тип коллектора, теги.
3. **Хранилище.** SQLite (stdlib) с идемпотентными миграциями при старте: уникальный индекс по
   каноническому URL (основная защита от повторов), индексы по дате, источнику, важности,
   релевантности, флагам. Ретенция раздельная: метаданные держатся долго, тела статей — коротко.
4. **Коллекторы.** Один базовый HTTP-слой: таймауты, повтор с backoff, учёт `Retry-After`,
   лимит размера ответа, только http(s) и защита от SSRF. Падение источника — результат с
   пометкой ошибки, не исключение. Общий бюджет времени прогона закрывает оставшиеся задачи
   тоже пометкой, а не отменой всего сбора.
5. **Дедупликация.** Канонический URL → нормализованный заголовок → похожесть токенов с окном
   последних заголовков из базы. Решение «дубликат» логируется, чтобы потом объяснить потери.
6. **Фильтр повестки до всего дорогого.** Сначала бесплатный детерминированный слой (ключевые
   слова по заголовку и описанию, теги — вторично), затем разметка; в LLM уходят только
   отобранные кандидаты и только в пределах бюджета на прогон и на сутки. Попадание в кэш
   не тратит токены.
7. **Релевантность — аддитивные бонусы по профилю интересов**, который хранится в базе и
   редактируется командой. Множители-штрафы за уровень схлопывают скор ниже любого порога, и в
   дайджест не попадает ничего.
8. **Дайджест — обычный текст карточками.** Заголовок, источник, время, категории, сводка,
   ключевые пункты, «почему важно», уровень релевантности, каноническая ссылка. Длинные
   сообщения резать штатным сплиттером хоста; ключевые пункты не дублировать со сводкой.
9. **Расписание внутри процесса хоста** (тик рядом с его основным циклом), без новых демонов.
   Отметки «что и когда отправлено» хранить в базе — тогда перезапуск не даёт повторную рассылку.
   Ручной сбор обязан блокировать параллельный прогон.
10. **Доставлять туда, где хост уже доставляет:** чат + заметки. Заметки писать ШТАТНЫМ API
    хранилища заметок (его каталоги и типы), новых каталогов не изобретать.
11. **Проверять по возрастанию цены:** юнит-тесты с заглушками (сеть и LLM запрещены) → импорт и
    сборка роутеров → живой прогон сбора на 6-10 источниках с печатью «источник → собрано/ошибка»
    и времени → глазами 10-15 отрендеренных карточек на мусор → один дешёвый живой вызов LLM
    (JSON разбирается, категории осмысленны, токены учтены).

## Ловушки

- **Темы на уровне источника — слабый сигнал, иначе каждая новость ленты получает ярлык
  источника.** Блог про модели с тегом AI Coding делал «AI Coding» из поста про морских львов.
  Категории выводить из заголовка и описания; теги и тело — вторичны; ужесточать только для
  заведомо тематических каналов (официальные блоги, научные разделы). Найденный мусор лечится
  правилом в коде и тестом на этот случай, а не фильтром пост-фактум.
- **Качество источника ≠ важность.** Важность выводить из содержания (первичность анонса,
  тип материала), иначе весь «надёжный» фид помечается важным и порог перестаёт работать.
- **Пустой фид в выходные/праздники — норма** (научные анонсы не выходят). Не удалять источник
  и не считать это ошибкой коллектора.
- **Старые даты публикации в фидах** дают маленький «дайджест за 24 часа» — это не поломка сбора.
  Хранить UTC, рендерить локальное время.
- **Неограниченный отбор кандидатов в LLM = взрыв стоимости.** Бюджет на прогон и на сутки,
  счётчик — из журнала в базе (не из памяти процесса), плюс кэш ответов.
- **Идемпотентность расписания только в базе.** Память процесса теряется при перезапуске и
  рассылка дублируется.
- **Запуск подсистемы в `try/except` глотает ошибки проводки.** Обёртка нужна (новая фича не
  должна ронять хост), но любая ошибка внутри блока — в т.ч. `NameError` от имени, которого нет
  в области видимости точки входа (напр., локальной переменной нет, а есть модульный геттер) —
  оставляет фичу **молча выключенной**: ни строки в логе, ни артефакта, ни падения. Перед
  правкой хоста читать его реальные имена (grep по определению, не по памяти). Так как точку
  входа (запуск бота/сервера) тестами не поднять, единственный дешёвый барьер — регресс-тест,
  который читает исходник хоста и требует в блоке проводки конкретные вызовы (геттер хранилища +
  `start()`); он ловит именно тот класс ошибок, который модульные тесты пропускают.
  После деплоя старт доказывать артефактом (созданный файл БД с записями), а не отсутствием ошибок
  в логе.
- **Проверочные команды не связывать в одну строку через `&&`:** упавший на гварде подтверждения
  фрагмент уносит с собой и безобидный тестовый прогон. Смоук-проверки импорта/сборки делать
  через `execute_code` (subprocess, venv-питон), тесты — отдельной командой.
- **Зелёный тестовый прогон не доказывает, что живой хост уже работает на новом коде.** Пока не
  выполнен перезапуск (а он требует согласия пользователя), так и говорить: «код проверен тестами,
  живой прогон — после перезапуска».
