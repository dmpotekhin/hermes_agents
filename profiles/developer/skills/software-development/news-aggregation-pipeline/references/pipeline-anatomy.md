# Каркас пайплайна: модули, контракты, настройки

Скелет подсистемы агрегации новостей, рассчитанный на встраивание в существующий хост
(бот или сервис) без переписывания. Пути примерные — важно разделение обязанностей.

## Разложение по модулям

```
<feature>/
├── config.py          настройки из env: from_env() + read_settings(), _env_bool/_env_int, parse_weekday
├── models.py          Source, Item, CollectResult/CollectReport, уровень-константы, utc_now
├── taxonomy.py        категории, ключевые слова, профиль интересов, is_relevant(), match_categories()
├── registry.py        реестр источников как данные (группы, приоритет, тип коллектора, теги)
├── textutil.py        нормализация URL/заголовков, чистка текста, first_sentences, похожесть
├── service.py         пайплайн сбора и выборок; единственная точка входа для хендлеров
├── scheduler.py       тик-цикл: сбор по интервалу, дневной/недельный дайджест, ретенция
├── ask.py             ответы по накопленной базе (сначала поиск, потом LLM с цитатами)
├── notes_sync.py      запись дайджестов в хранилище заметок хоста
├── collectors/        base (HTTP), rss, github, youtube, web + фабрика
├── processors/        deduplicator, classifier, llm, relevance, summarizer, trend_detector
├── storage/           migrations (идемпотентная схема), repository (save/query/stats/настройки/журнал)
└── digest/            daily, weekly, format (карточки + split)
```

## Контракты

- `CollectResult`: источник, список элементов, признак ошибки и её текст, время. Наружу никогда
  не бросает исключение; сервис собирает отчёт и продолжает.
- `build_item(source, title, url, ...)`: обязательны заголовок и http(s)-URL; канонизация URL
  выполняется здесь; темы источника подмешиваются только как слабая подсказка и только когда
  по содержимому не сработало ничего.
- `is_relevant(item)`: доменный фильтр (для AI-повестки — модели, агенты, инструменты, железо,
  обучение/инференс, безопасность, бизнес), режет ленты общего назначения по ключевым словам
  заголовка и описания.
- `classify(item)`: детерминированный слой доступен всегда (категории, тип материала, теги);
  LLM-слой опционален и возвращает строгий JSON с безопасным извлечением и нормализацией
  синонимов уровней (`very_high`→`high`), при ошибке — фолбэк на детерминированную разметку.
- `score(item, profile)`: аддитивная сумма бонусов (совпадение категории/тега/сущности/порога),
  без множителей-штрафов; профиль читается из базы, а не из кода.
- `render_card(item)`: заголовок, источник, время, категории, сводка, ключевые пункты, «почему
  важно», уровень релевантности, каноническая ссылка. `render_digest()` ограничивает число
  карточек, `split_message()` режет по лимиту транспорта.
- `save_note(digest)`: через API хоста, тип заметки отдельный (например `ai-news`), имя файла —
  дата + вид дайджеста; неудача записи не должна ломать отправку в чат.

## Встраивание в хост: точки касания

| Точка | Как делать |
| --- | --- |
| Запуск планировщика | задача рядом с основным циклом хоста (его же паттерн), внутри `try/except`; хранить задачу и останавливать при завершении |
| Хранилище заметок | ШТАТНЫЙ геттер хоста (вида `get_<storage>(config)`), а не локальная переменная: в точке входа локальной `vault` обычно нет |
| Регистрация роутера | до роутера с catch-all, иначе кнопки раздела не перехватываются |
| Клавиатура и callback | константа кнопки + запись в нижнюю клавиатуру и словарь текстов; отдельный префикс callback-данных |
| Хендлер раздела | один модуль: хаб + команды, поверх сервиса; aiogram внутрь сервисного слоя не протекает |

## Проверка после деплоя

1. Перезапустить службу хоста (`launchctl kickstart -k gui/$(id -u)/<label>` — под launchd).
2. Доказательство старта — АРТЕФАКТ: появился ли файл базы и есть ли в нём строки
   (`ls -l <db>`, `sqlite3 <db> "select count(*) from items;"`). Инициализация сервиса создаёт
   файл сразу при старте, поэтому его отсутствие = подсистема не поднялась.
3. Лог под launchd — блочно буферизованный: отсутствие свежих стартовых строк в первые
   десятки секунд ничего не доказывает, не делать из этого ложный вывод «упало».
4. Если артефакта нет — искать причину в самом блоке запуска (глотание ошибки общим `except`),
   а не в модулях пайплайна: модульные тесты эту проводку не покрывают.

## Реестр источников: что проверять при добавлении

| Проверка | Зачем |
| --- | --- |
| HTTP 200 и разбирается как RSS/Atom/RDF | иначе строка реестра выглядит рабочей, а коллектор всегда пуст |
| Число элементов > 0 (с оговоркой про выходные) | пустой ответ может быть нормой для научных фидов |
| Язык и тематика | русскоязычные и узкие каналы полезнее общих в общем потоке |
| Есть ли стабильный фид у официального блога | нет — пометить выключенным и типом `web`, не выдумывать адрес |
| Нужен ли токен | контур без токена честно показывает причину, а не молчит |

## Порядок обработки (стоимость растёт сверху вниз)

```
сбор → нормализация → канонизация URL → дедуп → фильтр повестки →
детерминированная разметка → отбор кандидатов → LLM (бюджет) → релевантность →
сохранение → дайджест → доставка (чат + заметки)
```

## Группы настроек

- включение подсистемы, язык, часовой пояс, путь к базе;
- расписание сбора и дайджестов (день недели, время), ретенция метаданных и тел статей;
- LLM: включён, режим, максимум материалов за прогон, суточный лимит вызовов, токены, температура;
- источники: явный список, отключённые, лимит материалов с источника, таймауты, повторы, backoff,
  лимит размера ответа, лимит символов текста;
- дедупликация: порог похожести заголовков, окно истории;
- дайджест: максимум карточек, минимальная важность и релевантность;
- внешние контуры: GitHub (список наблюдения, темы, глубина, число запросов), YouTube (каналы),
  заметки (вкл/выкл), поиск и тренды, уведомления в чат.

## Команды раздела (типовой набор)

Свежие материалы, брифинг, тематические подборки, GitHub-контур, недельный отчёт, тренды,
сохранённые, вопрос по накопленной базе, профиль интересов, список и переключение источников,
статистика, ручной сбор. Плюс кнопка в нижней клавиатуре, префикс callback-данных и кнопки
карточек (сохранить / похожие).
