# Медиа-фичи в существующем Telegram-боте

Как добавлять работу с медиа (кругляшок/video note, превью, извлечение звука,
нарезка) в уже работающий бот, не ломая существующий пайплайн. Опирается на опыт
`~/projects/tg-transcriber`, но правила общие для любого aiogram-проекта.

## Порядок работы

1. **Аудит до кода.** Найти: фреймворк и точку входа; хендлеры, принимающие медиа
   (`F.video | F.video_note | F.document`, отдельно `F.voice | F.audio`); где
   скачивается файл; где живут временные каталоги; существующие вызовы ffmpeg
   (`grep -rln "ffmpeg"`); как читается конфиг; тесты этой области.
   Проверить состав API: `python -c "from aiogram.types import Message; print(hasattr(Message, 'answer_video_note'))"`.
2. **Один слой ffmpeg.** Если ffmpeg уже используется, переиспользовать общий
   низкоуровневый модуль (запуск процесса, probe, длительность, наличие аудио) и
   делегировать туда старый код, сохранив прежние имена как обёртки — существующие
   вызовы тогда не меняются. Второго запуска subprocess в новом сервисе быть не
   должно.
3. **Сервис без фреймворка + тонкий хендлер.** Конвертация/обработка — в модуле,
   который не импортирует aiogram (принимает путь к файлу и каталог вывода,
   возвращает dataclass-результат). Скачивание, отправка и статусы — в хендлере.
4. **Сначала RED, потом GREEN.** Юнит-тесты сервиса с подменённым раннером
   (ffmpeg не нужен); отдельный файл интеграционных тестов с настоящим ffmpeg под
   `skipif(shutil.which("ffmpeg") is None)` — источник генерируется локально через
   lavfi, сеть не используется.
5. **Живая проверка перед «готово».** Юнит-тесты не доказывают, что Telegram
   примет файл: сгенерировать исходник, прогнать через сервис, отправить владельцу
   реальным вызовом и получить `message_id`. Готовый скрипт —
   `scripts/live_video_note_check.py` (квадрат, звук, отправка).
6. **Перезапустить бота** после подключения фичи, иначе кнопки/команды в чате не
   появятся: работающий процесс файлы не перечитывает. Живость — `getMe`
   (по логу не судить: свежие строки старта могут не успеть сброситься в буфер).
7. **Полный прогон + линтер + скан секретов перед коммитом**; количество тестов
   до/после фиксировать (существующие обязаны остаться зелёными).

## Правила и ловушки

- **Присланное медиа ловит первый зарегистрированный роутер, а не единственный.**
  Несколько хендлеров могут матчить `F.video`/`F.video_note`; срабатывает тот, чей
  роутер включён раньше (типичный перехватчик — catch-all «умный ответ» на
  `StateFilter(None)`), остальные не вызываются вообще. Симптом: пользователь
  «новой кнопки/фичи не видит», хотя тесты и импорт-проверка зелёные, а в логе нет
  ни одной строки нового хендлера. Поэтому после аудита — `grep -n "F.video\|F.video_note" handlers/*.py`
  и проверка порядка роутеров, а новое действие для уже присланного медиа
  добавлять веткой в ТОТ обработчик, чью клавиатуру пользователь видит (один путь,
  уже скачанный файл — не скачивать второй раз).
- **Кнопка под медиа обязана быть reply на сообщение с медиа.** Bot API не отдаёт в
  callback чужие сообщения: исходный `file_id` доступен только через
  `callback.message.reply_to_message`. Отправлять предложение с
  `reply_parameters=ReplyParameters(message_id=...)`, а обработчик сверяет
  `reply.message_id` с id из `callback_data`. Резерв — кэш `file_id` по `message_id`
  (TTL десятки минут), чтобы кнопка работала и без reply; после перезапуска бота
  честно просить прислать медиа заново.
- **Отправка именно нужным типом API.** Для кругляшка — `answer_video_note`
  (не `video` и не `document`): круг рисует сам Telegram, маску не накладывать.
  Держать это тестом: у fake-сообщения `answer_video` бросает `AssertionError`,
  тогда тест не пропустит отправку обычного видео.
- **Лимиты video note:** квадрат, ≤ 60 с, ≤ ~12 МБ. Значит: центр-кроп в квадрат
  (стратегия кропа из конфига, default `center`), масштаб до разумного размера
  (640x640 хватает), обрезка по `-t`, отклонение слишком длинного исходника и
  проверка размера файла после кодирования.
- **Звук сохранять.** `-an` только если в исходнике нет аудиодорожки; видео без
  звука обязано отправляться нормально, а не падать.
- **Свой лимит ≠ потолок Telegram.** Настройка вида `MAX_VIDEO_MB` проверяет лишь
  размер заявленный в апдейте; облачный Bot API отдаёт боту файл через `getFile`
  только до 20 МБ, поэтому бот с лимитом «100 МБ» упадёт на скачивании
  (`Bad Request: file is too big`) и ответит общей ошибкой. Перед поднятием своего
  лимита проверить транспорт: если сессия собирается как `Bot(token=...)`, локального
  API-сервера нет и большие файлы невозможны. Рабочие варианты: (а) локальный Bot API
  server со флагом `--local` + `AiohttpSession(api=TelegramAPIServer.from_base(...))` —
  снимает лимит скачивания (отправка до 2000 МБ), но требует `api_id`/`api_hash` и
  становится единой точкой отказа; (б) скачивание ПО ССЫЛКЕ (yt-dlp/прямой URL) —
  Telegram вообще не участвует; (в) честно оставить лимит 20 МБ. Минимум при поднятии
  лимита без локального API: предупреждение в лог при старте + отдельный понятный
  текст на «too big» вместо общей ошибки. Таблица, цена и порядок внедрения —
  `references/telegram-file-limits.md`.
- **У провайдера распознавания свой лимит на входной файл** (у Groq ~25 МБ аудио).
  Размер извлечённого аудио ИЗМЕРЯТЬ на реальном длинном файле, а не считать, что
  «очевидно влезает»: иначе фича проходит короткий смоук и падает на часовой записи.
  Не влезает — нарезать аудио по длительности и сдвигать таймкоды сегментов.
- **Идемпотентность по callback.** Двойной клик по кнопке запускает конвертацию
  дважды: держать состояние `processing/completed/failed` (TTL), на повторный
  клик отвечать алертом «уже готово/уже готовлю».
- **Всегда чистить временное.** Один `TemporaryDirectory` на запрос, `try/finally`;
  удалять и при ошибке. Имена выходных файлов — свои (uuid), не пользовательские:
  путь из чужих данных в командную строку не тащить, `shell=True` не использовать
  (только список аргументов), на таймауте убивать процесс.
- **Сервисные ошибки несут `code`/`user_message`, а не `.message`.** Обращение к
  несуществующему полю внутри `except` роняет обработчик вместо аккуратного ответа;
  пользователю — короткий текст, технические детали (код ffmpeg, размер,
  длительность) — в лог отдельным событием.
- **В тестах хендлеров подменять функцию показа (`render`), а не объект события.**
  `isinstance(event, CallbackQuery)` с самодельным фейком уходит в ветку сообщения
  и падает на неожиданном `reply_markup`; надёжнее `monkeypatch` на `render` со
  сбором текстов/клавиатур в список — тогда проверяется и текст, и состав кнопок.
- **Не хардкодить размеры/лимиты**, если в проекте есть конфиг медиа: добавлять
  ключи в существующий конфиг-модуль и в `.env.example` (без секретов).
- **UI-тексты и клавиатуры держать там, где они уже живут** (обычно `handlers/*`,
  не точка входа). Правка кнопки не должна тянуть клавиатуры в модуль бота.
- **Не писать вторую реализацию того, что в боте уже есть.** Если уже есть распознавание речи (ffmpeg + Groq Whisper) и LLM-слой с маршрутизацией/кэшем, новую фичу строить поверх них: вынести общее ядро (`_groq_transcribe_core(audio_path, config, *, response_format)`) и оставить прежние функции тонкими обёртками, а сервису передавать колбэки extract/transcribe снаружи вместо импорта провайдера. Иначе вторая копия расходится с первой в квотах, повторах и разборе `verbose_json`; фича «работает», а расход и лимиты считаются мимо.
- **Сегменты провайдера бывают не словарями.** Ответ вида `verbose_json` приходит объектом (pydantic/`SimpleNamespace`), и код, который ждёт `Mapping` (напр. `Segment.from_dict(item)`), молча получает пустой текст и выбрасывает все таймкоды — субтитры/главы/цитаты исчезают без ошибки. Нормализовать элементы через `getattr` + ветку `Mapping`, пустые отбрасывать; проверить тестом и на словаре, и на объекте.
- **Таймкоды и цитаты не выдумывать.** Что модель вернула — притягивать к реальным сегментам расшифровки (`snap_to_segment_start`, нормализация клипов) и отбрасывать расхождения; субтитры строить только из таймкодов сегментов. Нет таймкодов у провайдера — артефакт не создавать и показывать предупреждение, а не подставлять тайминг «на глаз».
- **Транскрипт потреблять LLM один раз.** Длинный текст — дорогая часть: один проход → «бриф» (с чанками для длинных видео), дальше все форматы собирать детерминированно из брифа, а не гонять полный транскрипт на каждый артефакт.
- **Wiring проверять по `sub_routers`, и регистрировать модуль в ДВУХ местах.** `build_menu_router(module)` возвращает роутер, собственные `callback_query.handlers` которого пусты — подключённые разделы лежат в `router.sub_routers` (у каждого своё `name`), поэтому проверка `[sub.name for sub in router.sub_routers]` работает, а обход `callback_query.handlers` даёт пустой список и ложное «не подключилось». И модуль фичи должен попасть и в локальный `from handlers import (...)` внутри билдера, и в кортеж роутеров: пропущенный импорт не ловят ни тесты, ни `import handlers` — падает только запуск бота (`NameError`), который общий `try/except` в `main()` проглатывает; симптом — «кнопка/фича молча не работает».
- **Одиночные команды.** Гвард подтверждения режет составные и многострочные
  команды и `python -c`: проверки оформлять скриптом в `/tmp` и запускать одной
  строкой, сообщение коммита отдавать файлом (`git commit -F /tmp/msg.txt`).
  Признак остановки гвардом — «exit -1» без вывода; такую проверку считать
  НЕ выполненной и переделать.
