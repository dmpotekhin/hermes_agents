# GSD Core — обзор и применимость для разработчика

> **Для Hermes:** этот документ — аналитический обзор, не план реализации. Использовать как референс.

**Цель:** Разобрать архитектуру GSD Core и понять, чем он может быть полезен разработчику, использующему AI-агентов в повседневной работе.

**Источник:** https://github.com/open-gsd/gsd-core (MIT, npm: @opengsd/gsd-core, 6.7k+ звёзд)

---

## 1. Что такое GSD Core

**GSD Core** — лёгкий meta-prompting и spec-driven development фреймворк, который садится *поверх* AI-агентов (Claude Code, Codex, Copilot, Cursor, OpenCode, Kimi CLI и других) и навязывает им дисциплинированный цикл разработки. Не заменяет агента — даёт ему структуру.

Ключевая метафора: **Git. Ship. Done.**

---

## 2. Главные проблемы, которые GSD Core решает

### 2.1 Context Rot («гниение контекста»)

В любом AI-сеансе по мере накопления сообщений качество ответов модели деградирует:
- Модель начинает противоречить ранним решениям
- Стиль кода уплывает от изначальных соглашений
- Планы игнорируют требования, сформулированные в начале
- Модель галлюцинирует имена файлов, которые 20 сообщений назад называла правильно

Это не баг модели — это фундаментальное свойство transformer-внимания на длинных последовательностях. `/clear` помогает, но теряет непрерывность.

**Решение GSD Core:** вся тяжёлая работа (исследование, планирование, написание кода, верификация) выносится в *под-агентов со свежим контекстом* (до 200K токенов). Основной orchestrator остаётся «худым» — только маршрутизирует задачи.

### 2.2 Отсутствие общей памяти между сессиями

AI-агенты не помнят, что делали в прошлой сессии. Разработчик вынужден переобъяснять контекст.

**Решение GSD Core:** файловая система как persistence-слой. Вся информация живёт в `.planning/` — `STATE.md`, `CONTEXT.md`, `PLAN.md`, `RESEARCH.md`. Это человеко-читаемый Markdown. Можно коммитить в git.

### 2.3 Отсутствие верификации

AI-агент может написать код — но никто не проверяет, соответствует ли написанное тому, что планировалось.

**Решение GSD Core:** шаг Verify в цикле. Отдельный агент читает требования, контекст, план и результат исполнения — и проверяет покрытие.

## 3. Цикл разработки (Phase Loop)

```
Discuss → (UI design) → Plan → Execute → Verify → Ship
```

Каждый шаг существует, потому что защищает от конкретного класса ошибок:

| Шаг | Что делает | От чего защищает |
|-----|-----------|-----------------|
| **Discuss** | Фиксирует implementation decisions (библиотеки, стратегии, edge cases) | Планер не гадает — он читает `CONTEXT.md` |
| **Plan** | Исследует, декомпозирует, проверяет план | Неоднозначность не доходит до исполнения |
| **Execute** | Пишет код атомарными коммитами в параллельных волнах | Context rot; конфликты между параллельными задачами |
| **Verify** | Проверяет requirement coverage, decision coverage, goal alignment | Код написан — но не то, что нужно |
| **Ship** | Создаёт PR, архивирует фазу, обновляет `STATE.md` | Потеря контекста между фазами |

### Как это выглядит на практике:

```bash
/gsd-new-project    # новый проект
/gsd-onboard        # существующий код
/gsd-discuss-phase  # обсудить фазу
/gsd-plan-phase     # спланировать фазу (3 под-агента: researcher, planner, plan-checker)
/gsd-execute-phase  # исполнить (параллельные executor-ы в волнах)
/gsd-verify-phase   # проверить
/gsd-ship-phase     # отправить PR
```

## 4. Архитектура

```
USER → COMMAND LAYER (/gsd-* команды)
     → WORKFLOW LAYER (оркестрация: spawn subagents, manage state)
     → AGENT LAYER (свежий контекст на каждого агента)
     → CLI TOOLS LAYER (gsd-tools.cjs — утилиты, роутинг)
     → FILE SYSTEM (.planning/ — все артефакты)
```

**Ключевые принципы:**
- **Fresh context per agent** — каждый под-агент стартует с чистым контекстом
- **Thin orchestrators** — оркестраторы не делают тяжёлую работу
- **File-based state** — нет базы данных, только `.planning/` Markdown + JSON
- **Absent = enabled** — фичи включены по умолчанию

## 5. Структура `.planning/`

```
.planning/
├── PROJECT.md        # что это за проект
├── REQUIREMENTS.md   # требования
├── ROADMAP.md        # дорожная карта (milestones, phases)
├── STATE.md          # текущее состояние (какая фаза, что сделано, блокеры)
├── config.json       # конфигурация
├── phases/           # артефакты каждой фазы
│   └── 01-auth/
│       ├── CONTEXT.md      # implementation decisions (Discuss)
│       ├── RESEARCH.md     # исследования (Plan)
│       ├── PLAN-01.md      # план для executor #1
│       ├── PLAN-02.md      # план для executor #2
│       ├── VERIFICATION.md # отчёт верификатора
│       └── SUMMARY.md      # итог исполнения
├── research/         # общие исследования
└── docs/             # документация
```

## 6. Чем GSD Core полезен разработчику

### 6.1 Дисциплина в AI-разработке

Самое ценное — не техническая реализация, а **дисциплинированный процесс**. GSD Core навязывает:
- Не писать код, пока не зафиксированы design decisions
- Не исполнять, пока план не проверен на согласованность
- Не объявлять готовым, пока не пройдена верификация

Это именно то, чего не хватает при ad-hoc использовании AI-агентов.

### 6.2 Переживание сессий

`.planning/STATE.md` — это «spine» системы. Любой агент в любой момент может прочитать его и понять, где мы находимся. Это решает проблему «на чём мы остановились в прошлый раз».

### 6.3 Параллельное исполнение

Фазы декомпозируются на независимые планы. Executor-ы в одной волне работают параллельно — каждый со своим свежим контекстом. Это не просто «быстрее» — это предотвращает взаимное загрязнение контекста.

### 6.4 Верификация как гражданин первого класса

Отдельный шаг Verify с requirement coverage, decision coverage и goal alignment. Не просто «тесты прошли» — а «то ли мы построили, что планировали».

### 6.5 Мульти-рантайм

Работает поверх Claude Code, Codex, OpenCode, Copilot, Cursor, Windsurf, Antigravity CLI, Kimi CLI, Kilo, Trae, Cline, Augment Code. Не привязан к конкретному агенту.

### 6.6 Git-интеграция

Все артефакты — текстовые файлы. Можно коммитить `.planning/` в репозиторий. Команда видит не только код, но и design decisions, планы и верификацию.

## 7. Сравнение с текущим Hermes-процессом

| Аспект | Hermes (текущий процесс) | GSD Core |
|--------|--------------------------|----------|
| **Планирование** | plan skill → .hermes/plans/ | Discuss → Plan (subagents) → .planning/phases/ |
| **Исполнение** | delegate_task (subagents) | Execute (parallel waves, fresh context) |
| **Верификация** | requesting-code-review + verification-before-completion | Verify (отдельный агент, coverage check) |
| **Состояние** | memory tool + session_search | .planning/STATE.md — файловая система |
| **TDD** | test-driven-development skill | Встроен в план (acceptance criteria) |
| **Контекст** | Один сеанс, context rot накапливается | Fresh context per subagent |

**Вывод:** GSD Core и текущий Hermes-процесс решают одни и те же проблемы, но GSD Core делает это более системно и с более жёсткой дисциплиной. Hermes гибче (можно пропускать шаги), GSD Core строже (нельзя пропустить Verify перед Ship).

## 8. Конкретные идеи для интеграции

### 8.1 Использовать GSD Core как внешний фреймворк

Самый простой путь: установить GSD Core рядом с Hermes и использовать для structured-проектов:
- `npx @opengsd/gsd-core@latest` → устанавливает команды
- `/gsd-onboard` на QA Interview Trainer → генерирует `.planning/`
- Дальше вести разработку через GSD-команды, Hermes — для остального

**Плюсы:** минимальные изменения, можно пробовать без миграции
**Минусы:** два инструмента, две экосистемы

### 8.2 Адаптировать идеи GSD Core в Hermes-процесс

Взять лучшие практики и реализовать их в текущих Hermes-скиллах:
- Добавить `STATE.md` в проекты (текущее состояние фазы)
- Усилить verification-before-completion requirement coverage
- Добавить Discuss-шаг перед planning для фиксации design decisions
- Структурировать `.hermes/plans/` по фазам, как `.planning/phases/`

**Плюсы:** единый инструмент, постепенная эволюция
**Минусы:** нужно писать/адаптировать скиллы

### 8.3 Использовать GSD Core CLI-инструменты из Hermes

`gsd-tools.cjs` — набор CLI-утилит (инициализация состояния, роутинг команд, observability). Их можно вызывать из Hermes-скиллов:
- `gsd-tools.cjs init <workflow>` — загрузить контекст
- `gsd-tools.cjs state get/set` — управление STATE.md

## 9. Риски и открытые вопросы

1. **Сложность:** GSD Core добавляет процессуальный overhead. Для мелких задач (tiny-fix, quick-win) избыточен.
2. **Node.js-зависимость:** GSD Core — npm-пакет. Требует Node.js в окружении.
3. **Совместимость:** GSD Core рассчитан на Claude Code/Codex/OpenCode. Использование с Hermes потребует адаптации.
4. **Зрелость:** Проект активный (v1.7.0, 6.7k звёзд), но всё ещё быстро эволюционирует — ломающие изменения возможны.

## 10. Рекомендация

**Для разработчика, уже использующего Hermes:** самые ценные идеи GSD Core — это не столько код, сколько **процесс**:
1. **STATE.md как источник истины** для состояния проекта между сессиями
2. **Discuss перед Plan** — фиксация implementation decisions до начала планирования
3. **Verify как обязательный шаг** — не просто «тесты прошли», а coverage check
4. **Фазы вместо спринтов** — bounded units of work с чёткими границами

Имеет смысл **адаптировать эти идеи в Hermes-скиллы**, а не пытаться запустить GSD Core как отдельный инструмент. Текущие навыки (`plan`, `test-driven-development`, `verification-before-completion`, `requesting-code-review`) уже покрывают 70% цикла — остаётся добавить недостающие 30% (Discuss + STATE.md).
