# Browser Admin UI — Drive the Pipeline from the Browser

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Turn the Streamlit dashboard into a complete browser admin so photo upload → city processing → content generation → approval → scheduling → (dry-run) publish are all clickable in the UI, exactly mirroring what `cli.py` can do, no terminal needed.

**Architecture:** Keep ONE code path. `ui/dashboard.py` becomes a thin Streamlit shell over the SAME modules the CLI uses (`Scanner`, `ContentEngine`, `DraftManager`, `Scheduler`, `StatsService`, `ingest_photos`). Every action opens a fresh `Database`, runs one async service call, closes it — the pattern already proven by `_collect()` and `_ingest()` in this file. No new service layer, no HTTP round-trip to `app.py`. `app.py` stays as-is (read-mostly API); adding `approve`/`plan` endpoints there is NOT required for the browser flow (YAGNI).

**Tech stack:** Streamlit 1.62 (`st.tabs`, `st.dataframe`, `st.button`, `st.rerun`), asyncio.run wrappers, existing `modules/*`, aiosqlite, Pillow.

### Task 0: Add a reusable fresh-DB action wrapper

**Objective:** One helper that opens a fresh `Database` + `Config`, runs any async service callable, closes the DB, and returns its (JSON-serializable) result. Reused by every tab.

**Files:**
- Modify: `ui/dashboard.py` (after the `_ingest` helper)

**Step 1: Add the helper**

```python
async def _run(action, *args, **kwargs):
    """Open a fresh DB + Config, run `action(db, config, ...)`, close it."""
    db = Database()
    await db.connect()
    try:
        return await action(db, Config(), *args, **kwargs)
    finally:
        await db.close()


def _call(action, *args, **kwargs):
    """Synchronous wrapper for st.button callbacks (Streamlit runs sync)."""
    try:
        return asyncio.run(_run(action, *args, **kwargs))
    except Exception as exc:  # noqa: BLE001 - surface to the UI
        st.error(f"Action failed: {exc}")
        return None
```

```python
async def _collect_cities():
    async def _inner(db, cfg):
        cities = await db.get_all_cities()
        out = []
        for c in cities:
            photos = await db.get_photos_by_city(c.id)
            out.append({"id": c.id, "city": c.name, "year": c.year,
                        "status": c.status.value if hasattr(c.status, "value") else str(c.status),
                        "photos": len(photos)})
        return out
    return await _run(_inner)

async def _scan(db, cfg):
    from modules.scanner import Scanner
    archive = getattr(cfg, "archive", None)
    path = getattr(archive, "path", None) if archive else None
    if not path:
        return {"error": "no archive path (set archive.path in config.yaml)"}
    res = await Scanner(db, archive_path=path).scan()
    return {"cities_scanned": res}
```

**Step 3:** Per-city "Generate content" button (in the city row):

## Risks & Tradeoffs

- **Long-running actions block the UI** (content generation, scan). Acceptable for a local single-user tool; can be moved to `st.spinner`/background threads later (out of scope).
- **`asyncio.run` per action** re-creates a loop each time. Proven safe by the existing `_collect()`/`_ingest()` pattern, but the loop must never leave any task pending. All helpers use `try/finally: await db.close()`.
- **No auth / local-only.** The dashboard binds to `localhost` by default; do NOT expose it publicly without adding auth (out of scope).
- **Streamlit rerun re-executes the whole script.** Each action needs a fresh DB (already the design) to avoid aiosqlite dead-loop leakage.
